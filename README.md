# Infirmary — Brother Health Records

A dependency-free, single-page PWA with a System 7 Macintosh interface. Directory entries and timestamped notes are saved locally, with explicit Google Drive pull/merge/push sync.

## Run

From this repository, run `npm start` (Node/npm and Python 3 required), then open port 8000 locally. Alternatively serve this directory using any static HTTP server. No install or build step is required. Deploy these files to an HTTPS static host for home-screen installation and offline support. Do not open `index.html` as a file URL.

Use **+ New** to create a person, select them in the directory, and enter notes with Enter or Add. Notes appear oldest first, with timestamps displayed in the device's timezone. **Export JSON** downloads a backup. No sample health records are included.

## Required connection and desktop handoff notes

Every opening shows the Drive connection dialog and hides/disables the workspace until Google sign-in and a successful directory sync finish. Choose **Use Infirmary-BHR** or select a storage location after signing in; a remembered location syncs automatically. Escape, the dialog Close button and minimize cannot dismiss the required connection step. A failed initial sync leaves it blocked with a retryable error. Disconnecting or losing the active access token locks the workspace again. This frontend gate is not backend authorization and does not encrypt or remove existing localStorage records.

Right-click an empty desktop area to open its context menu, then choose **New Sticky Note**. Type a handoff message and select **Leave note**. The pastel-yellow card records the connected user's name and syncs immediately into `desktopNotes` in `people_directory.json`; the next connected user of that same Drive directory receives it during their opening sync. Drag cards to move them, or focus a card and use arrow keys. Drag a card to Trash (or focus it and press Delete) for the existing permanent-delete confirmation. Deleted card IDs sync so stale copies cannot restore them. A network failure can leave a handoff pending locally; verify successful sync before expecting the next user to receive it. Cards may contain protected information, so none are written into source, GitHub, logs or app-shell caches.

## Log out

The power symbol at the far right of the top bar opens **Do you want to log out?** Cancel or Escape keeps the session and draft. Log out waits for any current sync, records the logout request, then completes a fresh Drive sync before clearing protected browser data. If sync or storage cleanup fails, the session and records remain available for retry. Finish active uploads/record saves before logging out.

Successful logout removes directory JSON (including notes, sticky notes, photos' Drive references and event history) and remembered Drive folder settings from localStorage. It clears rendered records, editor drafts, file selections, photo blob URLs and in-memory account/record state, and locks/clears other open BHR tabs on the same browser origin. The next connection pulls records from Drive. Public frontend assets remain cached; non-sensitive display preferences are retained. Drive requests use `cache: no-store`; the service worker caches only explicitly listed frontend assets. Downloaded exports, screenshots, browser/OS backups and another device's sessions are outside this cleanup. Closing a tab/browser or using Disconnect is not this explicit logout-and-clear flow. This ends the BHR connection, not the browser's Google account; future backend staff sessions will be separate from the central Drive connection.

## Event Log

Double-click the clipboard icon at the top right of the desktop (or focus it and press Enter) to open the read-only Event Log window. Events appear newest first and record actor, UTC creation time, action, affected entry ID, and changed field names. Record creation/updates/deletion, clinical note entry/edits/deletion, folder attachment changes, profile-photo and other uploads, sticky creation/movement/deletion, Drive connections/disconnections and directory-location selections are recorded. Read-only viewing, mouse movements, window geometry and unchanged periodic syncs do not add noise. Logout requests are recorded before the final sync; a request is not proof that sync and cleanup succeeded. Logging begins with this version; past activity cannot be reconstructed retroactively.

Data mutations and their event metadata are saved together in browser directory JSON. Existing event IDs cannot be edited or removed through normal application actions, including deleting a person or note. Cross-user sync unions entries and rejects changes under an existing event ID. Clinical note text, record field values, attachment bytes and credentials are not copied into the log. File IDs, person IDs and staff identities remain protected information. Only synthetic test metadata belongs in source.

Successful directory sync maintains `eventLog` in `people_directory.json` and a separate UTF-8 **BHR_event_log.txt** in the same selected Drive folder. The text file is a compact tab-separated document with quoted/escaped string fields, newest first; it is human-readable and can be safely re-read. Existing events from both copies are recovered and merged before writing. Duplicate log filenames or an unrecognized/changed log stop sync rather than overwrite unknown history. If publishing the text copy fails after JSON saves, the app reports incomplete sync and retries later. Offline actions and disconnect events can remain locally pending until the next successful connection/sync.

“Immutable” here means append-only events and a read-only app interface, not tamper-proof storage. A user with direct Drive/localStorage access can alter or delete files outside the app. Client timestamps can be inaccurate, JSON/text writes are not atomic, simultaneous clients still have the existing Drive-write race, storage failures can prevent an event being durably recorded after an upload, and old app versions can discard new fields. Production enforcement, durable atomic audit recording, trusted timestamps and retention policies require the planned backend. Update all clients before relying on this log. No raw record values are retained in event text when an entry is deleted.

Shared desktop stickies remain removable by **any connected user**, regardless of creator. Only individual chronological clinical notes have the original-author deletion restriction.

## File uploads and protected information

On a person's page choose **Upload file…**. Attach a Drive folder first and connect Google. With one attached folder it is selected automatically; with several, explicitly select the destination. The browser accepts any file type and sends the file directly to Google's Drive resumable upload endpoint. No application server, GitHub API, repository file, localStorage entry, or service-worker cache receives the file contents. Files remain in memory only as browser File handles during selection/upload. A duplicate name creates a separate Drive file, not an overwrite. Upload failures retain the selection for retry; check Drive first if a timeout leaves the outcome uncertain. Drive permissions, quotas and browser/network limits still apply. The upload timeout is five minutes. This version does not resume an interrupted transfer.

Only frontend source, public configuration, documentation and synthetic test fixtures belong in this repository. All real person information, notes, birth dates, directory JSON and attachments are protected runtime data; never put them in source, fixtures, logs, screenshots, issue reports or commits. `people_directory.json`, `BHR_event_log.txt`, `uploads/`, local environment files and logs are ignored as an additional guard, not an access-control mechanism. Browser directory storage remains unencrypted; attachments themselves are not persisted locally by the app. Google Drive authentication and server-side access controls must be part of the production login design.

The top bar uses a monochrome System 7-style recreation of the supplied abbey emblem and the name.

## Windows and ages

Age appears below date of birth, calculated from a complete date in the device timezone; incomplete/invalid dates show no calculated age. Ages refresh while open. February 29 birthdays increment on March 1 in non-leap years.

On desktop screens at least 1000 px wide, the main window starts around 60% of screen width and 80% of available height, leaving more visible desktop. Smaller screens retain the responsive layout. Drag a title bar to move the main window or a dialog, use its minus button to minimize, and click its button in the bottom dock to restore. Drag the lower-right resize corner to resize. Focus a title bar and use arrow keys to move it with the keyboard. The square maximize button fills the viewport below the top menu; pressing it again restores the previous size and position, including a manually resized window. The bottom status bar remains in the window frame while directory/detail contents scroll. Browser resizing keeps windows reachable and adjusts a maximized window to the available workspace. Mobile touch resizing depends on browser support.

## Desktop and permanent deletion

Desktop icons occupy a grid anchored at the top right, filling downward before creating another column to the left. Future `.desktop-icon` elements added to `#desktop-icons` use the same grid. Event Log occupies the first top-right grid slot; Trash is separately anchored at the bottom right and comes forward during an entry drag so it can receive drops even when the main window is maximized.

Drag a directory listing or your own chronological note onto **Trash**. Individual chronological notes can only be dragged/deleted by their original connected Google account; legacy/unattributed notes cannot be individually deleted. Ownership is checked again when confirming, so a stale dialog cannot authorize a different account. Shared desktop handoff notes remain trashable by any connected user. The dialog asks **ARE YOU SURE YOU WANT TO PERMANENTLY DELETE THIS ENTRY?** Cancel is focused by default; only confirming removes the entry. Deleting a person also removes their notes and revision histories from this directory. There is no undo or recoverable in-app trash. For keyboard access, focus a person or note and press Delete. On touch devices, tap an entry to select it, then tap Trash for the same confirmation.

Deletion removes record content from local directory storage and propagates to the selected directory JSON on the next successful sync. Minimal deletion markers contain only person/note IDs, allowing updated clients to reject stale copies instead of resurrecting deleted entries. Attached Drive folders/files/photos, previously exported backups, and Drive version history are **not** deleted. This is not a secure-erasure guarantee for external copies. All clients must update to this version to honor deletion markers; old app versions can discard new metadata. Person/shared-desktop-note deletion remains available after confirmation; individual chronological-note deletion requires its original connected Google author. Production role/author authorization still belongs in the planned backend.

## People and attached folders

The New/Edit person form has last name, first name, optional middle name/initial, preferred name, and separate month/day/year birth-date boxes. At least one name must contain text; all other fields are optional, including individual birth-date boxes. Impossible dates are rejected. Preferred name is used for display when present, with the full legal name below it. Existing records from earlier versions are retained, including their original names and notes. Location is no longer requested or displayed. Middle name is saved and searchable, and appears between first and last names in directory and record full-name subtitles. Preferred display names remain unchanged; there is no separate middle-name detail line. The original requirement of at least one first, last, or preferred name still applies.

Living people appear first, followed by a heavy divider and deceased entries in muted plum. Both groups sort by last name, then first name, ignoring case. Entries without a last name fall back to their current display name; names are not guessed from legacy text. The divider is a button that collapses/expands deceased entries. It stays available whenever deceased entries match the search, even if no living entries match, and remembers its state on the device. Deceased people have a crucifix beside the avatar. The deceased checkbox directly enables the date input without an extra death-record heading.

Each person's **Drive folders → Attach folder…** supports multiple folder links. Paste a Google Drive folder URL and optional label, or browse using Google's folder picker after connecting. Links persist locally and sync in the directory JSON; attaching a folder does not upload files, move records, grant access, or change folder sharing. Each folder opens in Google Drive in a separate tab. Folder links from both copies are retained during merges.

## Editing records, notes, and profile photos

Use the small **✎** at the right of a directory entry or record header to edit the person. Names, birth date, additional information, deceased status, and photo can be changed without replacing notes or attached folders. A record changed by sync while its editor is open must be reopened before saving, preventing silent overwrites.

Check **This person is deceased** to enable the separate death month/day/year boxes. Enter only known parts: month, year, month/year, month/day or a full date are supported. A day without a month is rejected, including day/year. Unknown parts stay blank. Invalid dates and known-impossible future or pre-birth ranges are rejected; no day or year is invented. Deceased records show **Age at death**, calculated only with complete birth/death dates; their age does not keep increasing. Unchecking deceased clears the saved death date.

Both New person and Edit record accept JPEG, PNG, WebP, or GIF profile photos up to 10 MB. Connect Google before saving a photo. Its destination is automatic: the person’s first attached Drive folder, or the Infirmary-BHR storage folder when no person folder is attached. There is no photo-folder selector. A previous photo’s folder does not override this rule. Photos upload directly to Drive only when the form is saved. Directory JSON contains only `{fileId, folderId}` references: no base64, image bytes, public sharing URLs, or access tokens. Photos are fetched using the in-memory Google token and displayed via temporary object URLs; initials remain the fallback offline, signed out, or when an image is unavailable. Existing photos are not deleted when replaced. A failed local save after a successful upload can leave an unreferenced photo in Drive; review it there rather than automatically deleting files.

New signed-in notes show **Entered by [Google account name]** next to the timestamp. The stable Google account subject identifies ownership; a display name alone is not used for permission checks. Only that connected account sees the note's pencil and can save an edit. Clinical quick notes appear newest first by their displayed event date. The original timestamp/text, revisions and editor identity remain stored internally; the chart shows the latest edit timestamp without a history viewer. The creator can correct the event date/time in the editor; corrections are versioned and preserve the original creation timestamp. Signing out or switching accounts removes access to the previous author's editing controls. Legacy and signed-out notes are explicitly unattributed and cannot be edited or retroactively claimed. Signed-out quick entry remains available, with a hint explaining attribution.

These ownership checks and history validation run in the browser. They are useful application behavior, **not tamper-proof authorization or an enforced audit trail**: people with direct Drive/file access can change JSON outside the app. The proposed authenticated backend must enforce author ownership on the server before using this as a protected production records system. New Google consent may be requested for the identity scopes. If identity lookup fails, Drive can remain connected, but new notes stay unattributed and editing is unavailable.

## Google Drive setup

Until the client ID is configured in `config.js`, actual Google sign-in cannot run. The app explains that setup is missing rather than silently leaving a disabled sign-in button.

Sign in and click **Use Infirmary-BHR** to create/reuse one folder named **Infirmary-BHR** in My Drive. It contains directory JSON, the Event Log, desktop notes/folders and fallback profile photos. The BHR desktop represents this folder, not the top level of My Drive. The actual folder ID is remembered for the session. Selecting an existing Infirmary-BHR folder reuses it; selecting another writable folder creates/reuses an Infirmary-BHR child there.

On upgrade, the app validates and moves the recognized directory/Event Log from the previous location and BHR-tagged desktop items from My Drive into the container. It preserves file IDs, nested folder contents, authors and chart links. Legacy fallback profile photos move there during sync, with updated references; explicitly assigned person folders remain unchanged. Unrelated files are left in place. Duplicate containers, conflicting directory/log copies or malformed legacy files stop setup with an error rather than overwrite data. Partial moves are safe to retry. Reload other open BHR clients before upgrading so old versions do not continue writing to My Drive root. Nothing runs against Drive merely by deploying the frontend; organization happens on the next connected sync.

The normal connection flow is **Infirmary → Google Drive… → Continue with Google → Choose directory folder… → Sync directory**. Account selection and consent use Google's actual OAuth popup; folder selection uses Google's actual Picker. Both need one-time application registration by the site administrator. The connection screen does not expose technical configuration fields. A static site cannot supply its own valid Google client identity automatically.

1. Create a Google Cloud project; enable **Google Drive API** and **Google Picker API**.
2. Configure the OAuth consent screen and add test users while the app is in testing. Create an **OAuth 2.0 Web application** client.
3. Add the exact deployed origin to **Authorized JavaScript origins**. For this GitHub Pages deployment use `https://pearibou.github.io` (no repository path). Add `http://localhost:8000` for local development if needed.
4. Create an API key restricted to the Google Picker API and appropriate website referrers (for example `https://pearibou.github.io/*`). Find the project's numeric **project number**, not its text project ID.
5. Put the public client ID, Picker API key, and project number in `config.js`, then commit/deploy. These are public application identifiers; never put an OAuth client secret or access token in source. Connection configuration belongs to the deployment, not the sign-in dialog.
6. After configuring and deploying these identifiers, open Google Drive, continue with Google, choose a writable directory folder, then sync. Per-person folder URLs can be attached without any Google setup.

Sign-in requires a direct click and opens Google's standard popup. Popup cancellation, network errors, or missing configuration are reported without deleting local records. The app itself keeps its retro design; Google's account and picker windows use Google's own interface.

Sync finds `people_directory.json` in the chosen directory folder, validates it, merges people and notes by stable IDs, and uploads the result. A missing file is created; duplicate filenames and conflicting note IDs stop sync. People metadata uses its newest `updatedAt`. Original note text is immutable; author edits are stored as append-only revisions. Sync combines compatible revision chains and stops on competing edits rather than silently picking a winner. Tokens remain in memory, while public configuration and selected directory folder are remembered locally. Disconnect clears the token; revoke the grant in Google Account permissions when needed.

The app requests `openid email profile` to identify the connected Google account for note attribution, plus the full `drive` OAuth scope so it can find an existing JSON file in an arbitrary folder. Public distribution can require Google's verification/security review for this restricted scope. A production alternative is a `drive.file` implementation with access limited to explicitly selected files. A fresh app opening requires Google authentication, a directory location and a successful initial sync. The cached interface can load offline, but its workspace remains blocked until that connection succeeds. After a successful opening, brief offline note entry is possible while the in-memory Google session remains valid; reopening or expired access requires reconnection.

Sync runs every 10 seconds while the app is visible, online, connected to Google, and a backend folder is selected. The top-bar **↻** and **Sync directory** also trigger it manually. Requests never overlap in one tab; drafts and notes entered during a request are retained. Automatic sync never opens OAuth popups: reconnect manually when the in-memory access token expires. Google can throttle requests; sync failures leave local records intact. Sync is **not transactional across devices**. Avoid simultaneous sync by multiple users: the second read narrows the race window but cannot prevent a concurrent write. Export backups and enable Drive version history. Hidden/closed apps do not sync, and confirmed deletions propagate using ID-only deletion markers. OAuth failures and rejected writes leave local records intact.

## Install on a home screen

On iOS Safari, use Share → Add to Home Screen. On supported Android/desktop browsers, use the browser's install action. Installation requires HTTPS (localhost is accepted for development). The service worker caches the local shell only; it does not cache Google API responses. iOS can evict local data, so keep exports or Drive backups. Actual iOS/Android installation should be checked on physical devices before deployment.

## Data handling

Records are stored unencrypted in this browser's localStorage and, after manual or automatic sync while connected, your selected Google Drive folder. This prototype has no application login, access controls, audit enforcement, or encryption at rest under app control. Use synthetic data for evaluation; deployment with real health records needs an approved security/privacy design and organizational review. Local persistence failures are reported rather than silently discarding records. Other open tabs are blocked from editing after a storage change until reloaded.

JSON format: `{ "version": 1, "people": [...] }`. Each person contains `id`, a compatible display `name`, `firstName`, optional `middleName`, `lastName`, `preferredName`, `birthDate` (`month`, `day`, `year`, each optional), `driveFolders` (`id`, `name`), `info`, optional `deceased`, `deathDate` as optional month/day/year parts (legacy ISO date-only strings are still read), optional Drive `photo` reference, ISO `updatedAt`, and `notes`. Optional directory-level `deleted` metadata contains `people` IDs and `{personId,noteId}` note markers, and optional desktop-note IDs. Optional top-level `eventLog` stores append-only activity metadata. Optional top-level `desktopNotes` stores shared handoff text, author, timestamps and desktop coordinates. Legacy `room` values are preserved but not displayed. Each note contains `id`, original `text`, ISO `createdAt`, optional `authorId`/`authorName`, and an append-only `edits` chain (`id`, `parentId`, `text`, `editedAt`, `editorId`, `editorName`).

## Login architecture (proposal; not implemented)

GitHub Pages publicly serves the frontend. A JavaScript-only password screen would not enforce access to the site or protect browser-stored health records. Google Drive authorization currently protects only access to Drive, not the page itself. API keys and OAuth client IDs are public identifiers, not login credentials.

For a staff-only application, move the frontend behind an authenticated host/access gateway and use Google sign-in with an explicit allowlist of staff accounts. A small backend should verify identity tokens, issue secure HttpOnly sessions, enforce authorization on every data request, and manage the organization's Drive access server-side. The backend can retain refresh credentials securely so staff sign-in and the shared Drive connection are separate. Never embed refresh tokens or a shared account password in this repository. Choose the hosting/identity provider and authorized staff list before implementing this design.

With login, the local/offline cache also needs an explicit policy: avoid unencrypted health records in localStorage on shared devices; clear or lock user data on sign-out, and determine whether authenticated offline use is allowed. Protecting the hosted URL alone does not revoke records already cached on a device.


### Logout and presence

The top-bar power button confirms logout, waits for any active sync, then performs a fresh final sync before disconnecting. A failed final sync keeps the session open for retry; Cancel becomes available again. After successful sync, logout removes protected local records and remembered folder settings, clears UI/memory and other open tabs, then requires a new connection. Unsaved input drafts are discarded rather than posted automatically. Closing a tab or browser does not run this logout flow.

**Connected Users: N** opens a compact list. Currently it reports only the authenticated session in this browser, not all people using the shared Drive account. `presence.js` exports `setPresenceProvider(provider)` for future shared presence: `provider.subscribe(onUsers)` emits arrays of `{id, name}` and returns an unsubscribe function. The provider starts only during an unlocked session and stops at logout; stale callbacks are ignored. Supply this from a future authenticated backend with session expiry/heartbeats and authorization, without writing presence to the clinical directory or GitHub.


Person records optionally include **Allergies:** or **No known allergies** below age. The checkbox disables/dims the text field; saving it checked stores the no-known-allergies state and clears previously entered allergy text. Leaving both blank hides the line. These clinical fields follow existing protected directory storage, Drive sync and logout cleanup; the Event Log records field names only.


## Drive desktop notes and folders

Right-click empty desktop space for **New Blank Note** or **New Folder** (alongside New Sticky Note). Clinical notes support bold, italic, underline, bulleted and numbered lists. New notes receive a suggested timestamped name and current local date/time, both editable. Save writes immediately to Infirmary-BHR, or the current folder when created inside an open BHR folder. There is no offline document editing: failed writes keep the draft in memory, and closing/minimizing or switching notes retains unsaved drafts in memory. Returning to the note restores its draft without a discard prompt. When unfinished work exists, **Resume Unsaved Note…** appears in the desktop context menu and lists drafts by name. Save each note to persist it; disconnect/logout clears all active and paused drafts. Keep the page open while an unsaved draft exists.

Saved notes use a versioned `bhr-rich-note` JSON format containing sanitized formatting, note date, immutable creation time and Google author identity. They are not executable HTML files and are opened/formatted within BHR. Native Drive folders and note files are marked with private application metadata; unrelated files in My Drive are neither listed nor changed. File names, folder names, note bodies and chart links are fetched directly from Google with no-store requests and are not saved in the browser directory, service-worker cache or repository. Metadata-only activity events remain in the protected Event Log.

Desktop icons fill the existing grid from the top right. Double-click a note to open it, or a folder to browse it; Enter also opens. Each folder has an independent movable, resizable window. Reopening an already open folder focuses/restores its existing window. Minimized folders show their actual names and a small folder icon; renames update their dock entries. Sticky notes stay in the foreground. New Folder starts with an active selected **New Folder** name: type a name and press Enter or click away, or Escape to retain the default. Drag notes/folders onto a folder icon, or into another open folder window, to move them. Create nested folders from the folder toolbar/context menu. **Up** opens or restores the containing folder’s window; dragging an item from a folder onto empty desktop space returns it to Infirmary-BHR. A folder cannot move into itself or a descendant.

Right-click a note for Open, Rename note, Attach note to patient's chart, or Send to Trash (delete). Attachment links one person to the original Drive note; it does not move or duplicate the document. Attached notes appear under **Clinical notes** on that person's page. Reattaching selects a different chart. Read-only viewers can open chart links. Clinical notes' text, dates, names, location and chart attachment can be changed, and notes deleted, only by the Google identity that created them. Checks apply in the UI and immediately before Drive writes. Other creators' notes are read-only and cannot be dragged. Shared folders may be renamed/moved; only empty folders can be trashed, preventing indirect deletion of someone else's notes. Deletion requires confirmation and sends files to recoverable Google Drive Trash, not immediate permanent destruction.

Writes check the current Drive modification time and send If-Match when an ETag is available; conflicting edits require reopening rather than silently overwriting. These browser-side checks are not a substitute for server-enforced authorization. Anyone signing into the same central Google account has the same author identity, and direct Drive access remains outside BHR restrictions. The future individual-staff-login backend must enforce these rules independently. Logout clears document/editor/list state across open BHR tabs; live files remain in Drive.

## Medication lists

The person header now offers Demographics, Medications and Medical History. Demographics opens its information window; Medical History opens its spreadsheet-backed list. Medications opens a dedicated window backed by the private **Medication Lists (BHR)** Google spreadsheet directly inside **Infirmary-BHR**.

Enable [Google Sheets API](https://console.cloud.google.com/apis/library/sheets.googleapis.com) in the existing Google OAuth project. The current Drive scope also permits Sheets access. Open a person’s Medications and click **+ Add medication list** to initialize the blank spreadsheet and create a surname/first-initial tab. Tabs are created only when requested and remain linked by stable IDs after renaming. Existing unexpected cells are not overwritten.

Add/edit entries with dose, route, frequency, instructions, indication, prescriber and start date. Active and Discontinued views preserve treatment history. Discontinue keeps the row with its date/reason; Delete entry is confirmed and intended for errors/duplicates. Short courses accept an end date and optional time; a date-only endpoint stays active through that date. New templates use America/New_York; the workbook timezone governs subsequent checks. Overdue courses are processed at connection and list opening, with failed updates explicitly pending.

Saves go directly to Sheets; failures preserve the form. Medication contents are held in memory and cleared on logout, never stored in the repository, localStorage or service-worker cache. Client conflict checks reduce accidental overwrites but are not atomic across simultaneous users. See [the design and operational limits](docs/medication-list-design.md).


## Demographics and printing

**New person / Edit record → Additional information…** contains optional primary language, religion, place of origin, address, home/cell phones and preferred pharmacy (including optional address, phone and fax), with repeatable authorized contacts (name, relationship, phone, emergency flag) and insurance policies (insurer, plan, member/policy/group numbers, policyholder, phone and notes). These fields use the protected directory sync and existing edit-conflict checks. The Event Log records changed field names, without contact or policy values. **Demographics** opens the information in its own window. New sessions select the first living person in surname order; chart selection remains in memory during the session and is not carried across logout.

**Print…** in Demographics or Medications invokes the browser’s normal print dialog, including Save as PDF where available. A separate temporary document includes transparent abbey letterhead, legal/preferred name, DOB, allergies and printed time; medication documents include last-retrieved time and the workbook timezone. Medication table headings repeat patient identity; demographics contact tables omit that redundant row. Compact demographics sections sit side by side, addresses align under their values, and an available Drive profile photo appears as a square beside patient details. Unavailable photos are omitted. Printed tables use explicit widths within the page margins. Active medications print by default; an optional checkbox includes discontinued history. Medication printing rereads Google Sheets and checks short-course endpoints first. Read errors or pending course writes stop printing rather than printing a stale list. Save edits before printing.

Only the public letterhead image is added to the frontend shell cache. Print contents stay in a temporary same-origin frame, never in browser storage, the service-worker cache or GitHub. The frame clears after the print dialog closes and on logout/disconnect; browser/OS print queues and user-saved PDFs are outside BHR’s control. Print activity records a dialog request, not proof of a physical print or PDF save. The letterhead is a restored high-resolution transparent PNG, kept separate from the pixel emblem used in the app.


Clinical note chart buttons show document icons and creation timestamps, newest first (Drive creation time is the fallback for older files). New/updated note files also carry creation/event timestamps in private Drive metadata. Drive folders is the last patient section; Upload file sits directly beneath the record pencil. Demographics includes optional primary care provider and patient e-mail; the pharmacy display shows its name/address directly, with Phone/Fax only when recorded.

Quick-note and clinical-note editors offer a top Print button and a bottom-left Trash button. Deletion still requires the original author and confirmation; unsaved clinical notes are discarded only after a separate confirmation. Other authors can view/print clinical documents but cannot edit or trash them. Printing uses the current editor contents; unsaved changes are explicitly marked and are not saved as a side effect. Unattached notes print with letterhead and author/date information without inventing patient details.


## Medical History

Open **Medical History** on a person’s chart. **+ Add medical history** creates/reuses the private **Medical History (BHR)** workbook in Infirmary-BHR and initializes a surname/initial tab only when requested. A pre-existing blank Google spreadsheet with that name also works; unrecognized nonblank cells are left unchanged. Sheets API and the existing full Drive OAuth connection are required. Stable spreadsheet/sheet/entry IDs survive tab renaming and row shifts.

**Add diagnosis…** searches the bundled public ICD-10-CM catalog by condition text, common abbreviations (HTN, DM, CHF, COPD, GERD, CAD) or dotted/undotted code. Choose a result explicitly. A custom display name is optional and never changes the stored official title/code/edition. An uncoded condition can be entered with a name alone. Onset is optional and accepts YYYY, YYYY-MM or YYYY-MM-DD. Notes are optional. There is no status column or status control in this version. Entries can be edited and deleted with confirmation. These shared history entries follow the medication-list editing model; creator-only restrictions on clinical/quick notes remain separate.

The bundled edition is **FY2026, April 1 update**, effective April–September 2026, and is labeled as such in the UI. It is not a current FY2027 catalog. See [source, release limitations and update instructions](data/ICD10-NOTICE.md). Code/description search uses 74,706 leaf codes; it does not provide complete tabular instructional notes or automatically assign a diagnosis. The public JSON/module files may be cached with the frontend; search text stays in memory and is never sent to a lookup service. Patient entries go directly to Google Sheets, never to GitHub or persistent browser storage. Protected directory JSON stores only the workbook/tab link.

Writes use literal values and stable Google row metadata; forms survive failures, added-row retries use the same entry ID, and changed baselines stop edits/deletions. Deleting clears the row’s cells while retaining its marker, preventing positional deletion of the wrong row. As with medications, client checks are not atomic across simultaneous writers; a future backend must enforce stronger concurrency, audit and staff authorization. Medical History records the current Google identity and logs metadata-only actions. Logout/disconnect clears its views, search results, drafts and pending selection.


Medical History entries display **code — diagnosis name**, with monospaced codes. Dataset edition remains in the search/editor and protected saved data rather than being repeated in each list entry. **Print…** refreshes the history from Google before invoking the standard letterhead print dialog; failed reads stop printing. Custom display names are used in the report, while original code/title/edition remain in Sheets.

The desktop defaults to a light French Blue with the original 4px texture. Right-click empty desktop space → **Change background color…** to preview a preset or native custom color. Apply saves only the hex color in `infirmary.backgroundColor` on this browser; Cancel/Escape restore the saved appearance. This nonsensitive preference survives logout and is not synced to Drive.
